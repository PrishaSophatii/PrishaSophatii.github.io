2 bits per weight: what model compression teaches retail ML

Oct 2026 · 8 min read · Inspired by Apple's Foundation Models Tech Report 2025

Apple's 2025 foundation model tech report reads like a catalog of ways to spend less per token. It is written about language models, but almost every idea transfers to the problems an online store faces: rankers that must answer in milliseconds, traffic that spikes tenfold on launch day, and a growing list of LLM features competing for the same budget.

The numbers that caught my eye

  • On-device: decoder weights at 2 bits per weight via quantization-aware training (QAT), embeddings at 4 bits, KV cache at 8 bits.
  • Server: about 3.56 bits per weight using ASTC, a GPU texture compression format repurposed for model weights so decompression rides on existing hardware.
  • Quality cost: modest and mixed. Apple reports a 4.6% MGSM regression but a 1.5% MMLU improvement on device, and 2.7% / 2.3% regressions on the server, with low-rank adapters trained to recover quality.
  • KV cache sharing: 37.5% less KV memory on device by letting the second block reuse the first block's cache.
  • PT-MoE: the server model runs parallel "tracks" that only synchronize at block boundaries. With a track block depth of 4, synchronization overhead drops by 87.5%.

Lesson 1: Train for the deployment you will actually have

The jump from post-training quantization to quantization-aware training is the key idea. If a model will run at 2 bits, let it learn at 2 bits. In retail ML, the same principle applies to features. If a feature will be stale by five minutes at serving time, or approximated by a cache, train with that staleness. Training-serving skew is the quantization error of feature pipelines, and the cure is identical: simulate deployment during training.

# Train with the features you will really have at serving time
def make_training_row(event):
    snap = feature_store.as_of(event.ts - SERVING_LAG)   # not event.ts!
    return snap.features(event.item_id), event.label

Lesson 2: Recover quality with small, targeted adapters

Apple compresses aggressively and then trains low-rank adapters to win back what was lost. For a store, the parallel is a single strong, cheap base ranker plus small task-specific heads: one for search, one for accessories, one for trade-in messaging. The base model's cost is paid once; each head adds very little latency and can be retrained independently when a campaign changes.

Lesson 3: Memory is often the real bottleneck

KV cache sharing is a reminder that latency budgets are frequently about memory, not FLOPs. Retail systems hit the same wall in embedding tables: millions of product, query and context embeddings. Quantizing embedding tables to 8 or 4 bits and sharing towers between search and recommendations usually buys more headroom than shaving model layers.

Lesson 4: Design for parallelism, not just size

PT-MoE's insight is that communication, not computation, can dominate at scale. Fewer synchronization points mean better throughput on many devices. In a recommendation serving path, the equivalent is fan-out: retrieval from several candidate sources, feature lookups and model calls. Collapsing synchronous hops (for example, batching feature fetches per request instead of per candidate) is often the cheapest latency win available.

Lesson 5: Measure regressions per capability

Apple's honest reporting of a regression on one benchmark alongside an improvement on another is the right habit. A compressed ranker should be evaluated per segment: head versus tail queries, new versus returning visitors, each locale. An average NDCG that holds steady can hide a large regression on long-tail searches, which is exactly where compression tends to hurt.

Efficiency is a feature. It decides how many good ideas you can afford to ship.
