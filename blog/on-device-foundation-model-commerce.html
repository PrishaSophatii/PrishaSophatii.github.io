A 3B model in your pocket: guided generation for product Q&A

Oct 2026 · 9 min read · Inspired by Apple's 2025 foundation model update

In 2025 Apple opened its roughly 3 billion parameter on-device language model to developers through the Foundation Models framework. Two details in Apple's write-up stood out to me as someone who thinks about retail ML: guided generation and tool calling. Together they turn a small model into something you can trust inside a shopping flow, because its output is typed and its facts come from your own systems.

What Apple shipped

  • A compact model built for Apple silicon. The on-device model is split into two blocks at a 5:3 depth ratio, and the second block reuses the KV cache of the first. Apple reports that this cuts KV cache memory by 37.5% and improves time to first token.
  • Aggressive compression. Decoder weights are quantized to 2 bits per weight with quantization-aware training, and low-rank adapters recover quality.
  • Guided generation. Mark a Swift struct with @Generable, and the framework injects the schema into the prompt while an OS daemon applies constrained decoding so the response always parses into that type.
  • Tool calling. Implement the Tool protocol and the framework handles parallel and serial tool calls, using a model post-trained for tool use.

Apple is explicit that this model is not meant to be a general knowledge chatbot. That is exactly why it fits retail: you never want a shopping assistant inventing specs or prices from its weights.

The shape of a grounded product assistant

Consider a shopper on a product page asking "Will this case fit my iPhone 15 Pro and does it work with MagSafe?" A trustworthy answer needs three things: the shopper's question, the official compatibility data, and an output format the page can render (an answer, plus the products it refers to so the UI can link them).

import FoundationModels

@Generable
struct ProductAnswer {
    @Guide(description: "A short, factual answer for the shopper")
    var answer: String
    @Guide(description: "Product identifiers mentioned in the answer")
    var referencedProducts: [String]
    @Guide(description: "True only if the answer is fully supported by tool results")
    var grounded: Bool
}

struct CompatibilityLookup: Tool {
    let name = "compatibilityLookup"
    let description = "Returns official compatibility data for an accessory"

    @Generable
    struct Arguments {
        @Guide(description: "The accessory's product identifier")
        var productID: String
    }

    func call(arguments: Arguments) async throws -> String {
        try await Catalog.compatibility(for: arguments.productID)   // your source of truth
    }
}

let session = LanguageModelSession(
    tools: [CompatibilityLookup()],
    instructions: "Answer only from tool results. If unsure, say so."
)
let reply = try await session.respond(to: question, generating: ProductAnswer.self)
render(reply.content)

Because the output is a typed ProductAnswer, the page never has to parse free text. The grounded flag gives the UI a cheap safety valve: if the model says it is not fully supported by the tool result, show the spec sheet instead of an answer.

Where on-device beats server for retail

  • Personal context stays local. The device can know which products someone owns. A compatibility answer that says "this fits the iPhone you have" does not require sending the device list anywhere.
  • Inference cost scales with customers, not servers. Apple describes on-device inference as free of cost to developers. Peak events like a product launch would otherwise be the most expensive moment for an LLM feature.
  • Latency is predictable. KV cache sharing and low-bit weights are designed for fast first tokens, which matters on a product page where people skim.

Where the server still wins

Catalog-wide reasoning ("compare every Mac for video editing under a budget") needs fresh pricing, availability and more capacity. Apple's architecture already anticipates this with its larger server model on Private Cloud Compute. A good design routes simple, personal, grounded questions to the device and heavy comparative ones to the server, with the same typed output schema for both, so the UI does not care which one answered.

How I would evaluate it

  1. Groundedness: automatically check every claim in answer against the tool output. Track the rate of ungrounded claims, not just thumbs up or down.
  2. Abstention quality: measure how often grounded == false when the tool really lacked the answer (good) versus when it had it (missed help).
  3. Business impact: A/B test on downstream outcomes like add-to-cart for compatible accessories and fewer returns for incompatibility, rather than engagement with the assistant itself.
  4. Adapter drift: Apple notes adapters must be retrained for each new base model version, so the eval suite has to be a regression gate in CI.
Small models become trustworthy when you give them a schema to fill and a source of truth to read from.
